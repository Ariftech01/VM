ROLE
You are a senior AI systems engineer and full-stack developer acting as an autonomous coding agent. Build a complete, working, demo-ready proof of concept called "GitMem": Git-Style Versioned Memory for Efficient and User-Controlled AI Agents. It is for the L&T Techgium hackathon, problem statement PS-2 ("Efficient and User-Controllable Context Memory for Long-Running Agentic AI").

PROBLEM
Long-running AI agents accumulate messages, decisions, documents and tool results across many sessions. Sending the entire history to the model repeatedly increases token consumption, inference cost and latency. Conventional summarization or truncation can remove important information, make the agent lose context, and make mistakes hard to recover from. GitMem works like Git for AI memory: it keeps a versioned record of the agent's context, explains every keep/summarize/archive decision, and lets users restore earlier states, branch into alternatives and merge compatible changes. Context reduction becomes reversible, traceable and user-controllable.

The challenge requires: a working proof of concept, an inspectable interface, reversible memory management, and a comparison against baseline context-management approaches.

HARD CONSTRAINTS

CORE SYSTEM (base design; all must work)
1. Ingestion: split conversations and tool outputs into units of type turn / decision / code / constraint / fact / preference, each with topic label, timestamp, session id, token count.
2. Memory scoring engine: score = weighted combination of importance, relevance to current goal, redundancy penalty, recency decay and user-pin boost. Weights and thresholds are configurable in YAML. Each unit gets one action: KEEP_VERBATIM, SUMMARIZE or ARCHIVE, with a human-readable reason and the full score breakdown (explainable compression).
3. Tiered memory: pinned / hot (verbatim) / warm (summaries linked to their source units) / cold (archive). Originals are never deleted by default (reversible forgetting).
4. Versioned memory store (the centerpiece): every memory update creates a commit with SHA-256 hash, parent hash(es), branch, timestamp, message, topic, per-unit decisions and reasons, token counts before/after, and a snapshot of active-memory membership. Commits form a hash-chained DAG; provide a verify-integrity command that detects tampering.
5. Git-like operations: log, diff (between any two commits: units added/removed/changed tier, token delta), restore/checkout, revert, branch, merge, cherry-pick, tag/checkpoint, and manual edit (pin, unpin, force-keep, force-archive, edit text).
6. RESTORE vs REHYDRATE are different operations, separate in API, CLI and UI. Restore rolls the whole active memory back to an earlier commit. Rehydrate selectively pulls specific archived units back into the active context without changing anything else. The UI must make this distinction obvious.
7. Retrieval and context reconstruction: given a query and a token budget, build context = pinned facts + recent turns + relevant summaries + retrieved archived units, chosen by a value-per-token knapsack optimizer (not simple top-k). Return the context plus an explanation of every inclusion and exclusion.
8. Conflict-aware 3-way merge: detect contradictions (rule-based + embedding similarity + optional LLM check) and temporal supersession (a newer fact such as "deadline moved to Friday" replaces the older one with a recorded supersedes-link). Compatible changes auto-merge. True conflicts go into a queue for user resolution and are never silently overwritten.

NOVEL FEATURES (all must work)
9. Memory Blame: for any generated answer, show which units, commits and decisions fed it (like git blame), with contribution highlighted.
10. Memory Bisect: given a failing probe question, binary-search commit history to find the first commit that lost or corrupted the fact.
11. Canary facts / Memory CI: user marks critical facts with probe questions. After every commit, run the probes automatically; a failing commit is flagged and can be auto-reverted with one click.
12. Faithfulness gate: every summary must link to source unit IDs. A verifier checks that entities, numbers, dates and negations from the originals are preserved and that nothing new is introduced or contradicted. Failing summaries are rejected and the unit stays verbatim.
13. What-if replay: ask the same question on two commits or branches and diff the answers, tokens and latency.
14. Crypto-shred: an explicit, confirmed, IRREVERSIBLE delete for sensitive units (PII detected by regex), recorded as a tombstone in the hash-chained history so tampering stays evident. Reversible forgetting remains the default.
15. Cost dashboard: live tokens saved, estimated cost (configurable price per 1K tokens) and latency versus each baseline.
